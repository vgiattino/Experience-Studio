# Security Architecture

Status: **Draft for approval**
Related: [`architecture-review.md`](./architecture-review.md) · [`backend-architecture.md`](./backend-architecture.md) · [`ai-architecture.md`](./ai-architecture.md)

Experience Studio lets business users and a language model author artifacts that read regulated enterprise data belonging to multiple client organizations. The security architecture must hold when the author is unskilled, when the author is a model, and when the artifact has been tampered with.

---

## 1. Principles

These are the non-negotiables. Every design below is a consequence of one of them.

| # | Principle |
|---|---|
| **P1** | **A page definition is a statement of intent, never a security boundary.** Definitions are authored by business users and generated by a model. Both are untrusted with respect to entitlements. |
| **P2** | **One enforcement point.** All EDM access flows through the Data Gateway. There is no second path, no bypass, and no exception for preview. |
| **P3** | **Authorization is resolved from the caller's identity at request time.** Never from client input, never from a field in the definition, never from a cached decision of unbounded age. |
| **P4** | **Deny by default.** Absent an explicit grant, access is refused. Unknown is not permitted. |
| **P5** | **Experience Studio never widens data access.** It can narrow what a user sees; it can never grant what EDM has not granted. |
| **P6** | **Preview and production enforce identically.** Same gateway, same code path, author's own entitlements. |
| **P7** | **The model is an untrusted author.** Its output is validated data, never executed instruction. |
| **P8** | **Everything consequential is audited**, immutably, with actor and correlation. |

P1 and P5 are the two most likely to be eroded by convenience during implementation, and the two whose erosion is hardest to detect afterwards.

## 2. The Two Authorization Axes

The most common conceptual error available in this architecture is treating authorization as one thing. It is two, they are orthogonal, and conflating them produces either a data breach or an unusable product.

| | **Platform authorization** | **Data authorization** |
|---|---|---|
| Question | What may you *do* in the Studio? | What data may you *see*? |
| Examples | Create an experience, approve a publication, edit the catalog, administer roles | Which securities, which funds, which columns |
| Owned by | Experience Studio | **Opus EDM / enterprise entitlements** |
| Model | RBAC + resource scoping | Row-level predicates and column-level rules from EDM |
| Enforced at | Definition, Catalog, Governance services | Data Gateway |
| Granted by | Tenant Admin | The client's existing EDM entitlement administration |

Three consequences that must be stated explicitly, because teams reliably get them wrong:

1. **Publishing an experience grants nobody any data access.** Publication is a platform action. A viewer of a published dashboard sees exactly the data their EDM entitlements permit, and nothing more.
2. **The same page legitimately looks different to different users.** One user sees twelve widgets; another sees nine and three `denied`. Both are correct. This drives the runtime's independent per-widget statusing ([`runtime-architecture.md`](./runtime-architecture.md) §8) and must be treated as normal operation, not degradation.
3. **An author can create a page they cannot fully use.** An author entitled to fewer columns than their audience produces a page that renders more for the audience than for them. This is acceptable and must not be "fixed" by widening the author.

## 3. Identity and Authentication

| Aspect | Design |
|---|---|
| Protocol | OIDC / OAuth 2.1 against the client's enterprise IdP; SSO expected |
| Tenant | Resolved from a verified token claim, never from a header, path segment, or request body |
| Browser tokens | Short-lived access token held in memory only; refresh token in an `HttpOnly`, `Secure`, `SameSite` cookie. No token in `localStorage` |
| Session | Idle and absolute timeouts; step-up authentication for publication to production and for role administration |
| Service-to-service | mTLS or workload identity. No shared static secrets between services |
| EDM credentials | Held **only** by the Data Gateway |
| Model provider credentials | Held **only** by the Generation Service |
| Secrets | Managed vault, rotated, never in configuration files or images |

The two credential-scoping rows are architectural, not operational hygiene: they are what make P2 verifiable. If any service other than the gateway *could* reach EDM, no amount of code review establishes that it doesn't.

## 4. Platform Roles

Least privilege, with separation of duties on the paths that reach production.

| Role | Capabilities |
|---|---|
| **Viewer** | Open published experiences within permitted workspaces. No authoring |
| **Author** | Create and edit drafts, generate with AI, preview, save templates, submit for review. Publish to non-production only |
| **Reviewer / Publisher** | Review, approve or reject, publish to production, promote between environments, roll back |
| **Catalog Steward** | Author and publish catalog versions; classify sensitivity; manage logical data sources; resolve drift |
| **Template Curator** | Approve platform-curated templates and mark exemplar eligibility |
| **Tenant Admin** | Manage users, roles, workspaces, environment bindings, tenant policy (including AI opt-ins) |
| **Auditor** | Read the audit trail. **No data plane access, no authoring** |
| **Platform Operator** | Operate infrastructure. **No tenant data access, no definition content access** |

Two separations are deliberate and should not be collapsed for convenience:

- **Auditor and Platform Operator both lack data access.** Being able to run the platform must not imply being able to read a client's securities. This is the difference between an operable platform and a permanently privileged operations team.
- **Author ≠ Reviewer for production.** By default an author cannot approve their own artifact for production; the requirement is configurable per tenant, because some clients will accept the risk and others are contractually forbidden from doing so.

**Persona mapping** (closing review gap §G10): Business Analyst → Author. Data Steward → Author + Catalog Steward. Product Owner → Author, plus Reviewer in non-production. Professional Services → Author + Template Curator, and later a scoped Extension Developer role. Platform Administrator / Catalog Steward — the role the original persona list omitted — is a required first-class persona.

## 5. Permissions Model

**RBAC for actions, resource scoping for reach.** A permission is `(action, resourceType, scope)`.

| Scope | Meaning |
|---|---|
| `own` | Resources the user created |
| `workspace` | A named workspace, the unit of team sharing |
| `tenant` | All resources in the tenant |
| `platform` | Cross-tenant, curated platform assets only |

Workspaces are the sharing primitive, and they are what make governance tiering possible.

### Governance tiered by blast radius

This resolves the tension the review flagged between "AI-first speed" and "enterprise governance" (§G12). Governance weight scales with consequence rather than taxing every action:

| Artifact scope | Approval required | Rationale |
|---|---|---|
| Personal draft, unshared | None. Publishes to own view instantly | Preserves the minutes-not-weeks experience where users actually feel it |
| Workspace-shared | Workspace-level review | Peer visibility, low ceremony |
| Tenant-published | Reviewer approval | Real audience, real consequence |
| Production environment | Reviewer approval + separation of duties + audited promotion | Regulated surface |
| Platform-curated template | Template Curator approval + content scrub | Crosses tenant boundaries (§7) |

Governance that taxes every action uniformly gets routed around, which produces worse security than governance that is proportionate. This table is a security control, not a UX concession.

### Lifecycle transitions as authorization decisions

```
Draft ──submit──► In Review ──approve──► Approved ──publish──► Published ──deprecate──► Deprecated ──► Archived
  ▲                   │                                            │
  └──────reject───────┘                          rollback ─────────┘
```

Each transition is a permission check plus an immutable audit record. Published versions are immutable in storage ([`backend-architecture.md`](./backend-architecture.md) §4.2), so "editing a published page" is structurally impossible — it creates a new draft version.

## 6. Data Entitlement Enforcement

### 6.1 Where it happens

Only in the Data Gateway. Every query, from every source — Viewer render, Studio preview, AI cost estimation, export — resolves entitlements against the caller's identity.

The gateway pipeline, in order:

1. Validate token; resolve tenant, user, platform roles.
2. Resolve the logical data source to a physical target via `experience_binding` for this tenant and environment.
3. Resolve **data entitlements** from EDM for this user: row predicates and permitted columns.
4. **Reject any requested attribute not in the permitted set.** Never silently substitute or omit without signalling.
5. Inject row predicates into the query server-side. Client-supplied filters can only ever narrow further.
6. Apply cost guards: estimated rows, fan-out, timeout.
7. Execute; apply column masking where masking rather than denial is configured.
8. Return per-query status with an entitlement scope hash and TTL.
9. Write the audit record: user, data sources, resolved scope, row counts, duration, correlation id.

Step 4 is where P1 becomes concrete. The definition *asked* for `clientPnL`; the gateway decides whether the caller may have it. A tampered, copied, or hallucinated definition changes the question, never the answer.

### 6.2 Enforcement must be structurally verifiable

Code review is insufficient for a control this important. Three mechanisms:

- **Network policy:** only the Data Gateway may reach EDM. Enforced at the network layer, so a mistake in another service cannot reach the data at all.
- **Architectural test:** CI fails if any module outside the gateway imports an EDM client or holds EDM credentials.
- **Adversarial test suite** in CI, treating enforcement as a security control rather than a feature: hand-tampered definitions requesting denied columns; definitions copied between tenants; parameters crafted to widen row predicates; expressions attempting to reach outside their scope; cache probes for another user's rows. Any leak fails the build.

### 6.3 Catalog retrieval is entitlement-scoped too

A denied column is removed from the *catalog surface* the user sees, in Studio browsing and in AI retrieval alike ([`ai-architecture.md`](./ai-architecture.md) §3.2).

This serves two purposes at once. It prevents information disclosure — attribute names themselves can be sensitive, and "we have a `clientPnL` field" is a real leak. And it prevents authors from binding to fields that will fail at render, which would otherwise be experienced as unreliability rather than governance.

### 6.4 Cache keys must include the entitlement scope

Every cached query result is keyed by `(dataSourceId, paramsHash, entitlementScopeHash)`.

**This is the highest-consequence single line in the security architecture.** Omit the entitlement component and one user's rows are served to another from cache — a complete authorization bypass that no amount of correct enforcement code prevents, because enforcement is never reached. It is stated in three documents deliberately.

Entitlement resolutions are cached briefly and only briefly: revocation must take effect in minutes, not hours.

### 6.5 Publication-time warnings

When an experience is published, the platform lists the sensitive-classified attributes it binds. Reviewers approve with knowledge of what data the page exposes to its audience, rather than inferring it from widget titles. This is the control that makes reviewer approval meaningful rather than ceremonial.

## 7. AI-Specific Controls

The model is an untrusted author with network reach to a third party. Controls in layers:

| Layer | Control |
|---|---|
| **Placement** | Generation Service is server-side only. No provider credentials in any browser. Viewer has no AI surface at all |
| **Egress — default** | Catalog **metadata** only: business names, types, units, relationships, allowed aggregations. No customer records |
| **Egress — sample values** | Permitted only for attributes classified low-sensitivity, only with explicit per-tenant opt-in, never for PII or restricted classifications, and always through the entitlement-scoped retrieval path |
| **Untrusted content** | Client-originated text that must enter context (exception descriptions, override comments) is delimited and labelled untrusted; the system contract states such content is data to be described, never instruction to be followed |
| **Structural defense** | Model output is a declarative definition validated before use, never executed code. This is the primary injection mitigation — a successful injection can produce only a definition that fails validation |
| **Independent authorization** | Every generated binding is re-authorized at render time by the gateway. Retrieval scoping is a quality and disclosure control; it is never the enforcement point |
| **Tenant isolation** | Retrieval, exemplars, prompt caches and result caches are tenant-scoped |
| **Cross-tenant exemplars** | Only platform-curated templates, reviewed and scrubbed of client-identifiable content, may serve as few-shot examples across tenants |
| **Provider terms** | No training on client data; bounded retention; region-pinned inference for residency |
| **Rate and cost** | Per-user and per-tenant request and currency budgets enforced before provider calls, alerting well before the cap |
| **Provenance** | Prompt, prompt template version, model version, catalog and registry versions, retrieved concepts and exemplars recorded on every generated version |

**The template library is the least obvious leak path in the entire architecture** and deserves emphasis. Templates exist to be reused, exemplars exist to cross situations, and a client's dashboard is a description of that client's data model, naming conventions, and operational concerns. Allowing a tenant's template to serve as another tenant's exemplar would leak commercially sensitive structure without ever touching a data row. Hence `exemplar_eligible` is a curated, reviewed flag distinct from visibility, and cross-tenant eligibility requires a content scrub.

## 8. Tenant Isolation

Isolation in depth, because a single-mechanism failure must not be a cross-tenant breach.

| Layer | Mechanism |
|---|---|
| Identity | Tenant from a verified token claim only |
| Request | Tenant context bound at the request boundary and propagated; services never accept a tenant parameter from the client |
| Application | Every repository call is tenant-filtered |
| Database | `tenant_id` on every row + PostgreSQL row-level security bound to the session tenant |
| Storage tier | Optional isolated database or cluster for clients with contractual isolation requirements |
| Cache | Tenant-namespaced keys; entitlement scope in data keys |
| Vector index | Tenant-partitioned; retrieval never crosses partitions |
| AI context | Tenant-scoped retrieval and exemplars; cross-tenant only via curated platform templates |
| Audit and logs | Tenant-partitioned; no tenant identifiers or data values in shared application logs |
| Encryption | Encryption at rest and in transit; per-tenant keys with BYOK/CMK for clients requiring it |
| Residency | Region-pinned deployment **including the model provider region** |

Row-level security is explicitly defense in depth, not the primary control — application queries always filter by tenant. It exists because it converts a forgotten predicate from a cross-tenant breach into an empty result set. Given the asymmetry of consequence, the redundancy is cheap.

Residency including the inference region is easy to overlook and contractually material: a tenant pinned to an EU deployment whose prompts are processed elsewhere has not met its residency obligation.

## 9. Application Security

| Surface | Control |
|---|---|
| **Definition content as XSS vector** | Definitions carry author-supplied labels, titles and formats. Rendered as text through Angular's sanitization. No `innerHTML` from definition content. Rich text, if ever supported, through a strict allowlist |
| **Expression sandbox** | No `eval` or `Function`; whitelisted function set; no access outside the supplied scope; no network or DOM reach; bounded evaluation cost; deterministic and side-effect free |
| **Definition tampering** | All definitions revalidated and re-authorized server-side on save and on publish. The `security` block is authoring intent only and is never an enforcement input |
| **Frontend hardening** | Strict CSP, no inline script, Subresource Integrity, Trusted Types where supported |
| **API hardening** | Schema validation on every payload, size limits, rate limits, idempotency keys, origin checks |
| **Export and sharing** | Exports carry the *exporter's* entitlements and are audited as data egress events. A shared PDF is a copy of entitled data leaving the platform, and must be treated as such |
| **Custom components** (future) | Review gate before registration; no direct EDM access (gateway only); no arbitrary network egress; CSP-constrained; versioned and revocable |
| **Dependencies** | SCA scanning, pinned lockfiles, signed builds, SBOM per release |

The export row is frequently underestimated. Every governance control in this document applies to data on a screen; a PDF or spreadsheet leaves the perimeter entirely. Auditing it is the minimum.

## 10. Audit

Append-only, tenant-partitioned, long-retention, no `UPDATE`/`DELETE` grants to any application role, readable by the Auditor role without any data plane access.

| Category | Recorded |
|---|---|
| Authentication | Sign-in, failure, step-up, session termination |
| Platform authorization | Denied actions with attempted action and scope |
| Definition lifecycle | Every transition: actor, from/to state, version, approval reference |
| Definition content | Every patch: actor, origin (`user` / `ai` / `migration`), diff |
| Generation | Full provenance per [`ai-architecture.md`](./ai-architecture.md) §5.6 |
| Data access | Every query: user, data sources, resolved entitlement scope, row counts, duration, correlation id |
| Promotion | Environment, versions, approver, binding resolution used |
| Administration | Role, catalog, registry, binding and policy changes |
| Egress | Exports, shares, print |

The design requirement: a reviewer or regulator can reconstruct, for any page running in production, **who asked for it, what prompt and model produced it, what catalog it was bound against, who reviewed and approved it, when it was promoted, and every query it has issued since** — from the audit trail alone. That end-to-end reconstruction is only possible because a single correlation id threads prompt → definition version → render → query.

## 11. Threat Model

| # | Threat | Primary control | Backstop |
|---|---|---|---|
| T1 | Author hand-edits a definition to request denied columns | Gateway rejects unpermitted attributes (P1, §6.1 step 4) | Adversarial CI suite; query audit |
| T2 | AI hallucinates a binding to sensitive data | Entitlement-scoped retrieval; validation stage 5 | Gateway re-authorization at render |
| T3 | Definition copied between tenants | Tenant-bound identity; RLS; binding resolution is tenant-scoped | Architectural test; audit |
| T4 | Cached rows served across users | Entitlement scope in cache key (§6.4) | Cache-probe tests in CI |
| T5 | Prompt injection via client data in context | Delimited untrusted content; output is validated data, never code | Validation cascade; gateway re-authorization |
| T6 | Cross-tenant leakage via shared templates/exemplars | Curation gate + content scrub; `exemplar_eligible` separate from visibility | Tenant-partitioned retrieval |
| T7 | Privilege escalation via lifecycle transitions | Permission check per transition; separation of duties | Immutable audit of every transition |
| T8 | XSS through authored labels | Text-only rendering, Angular sanitization, strict CSP | Trusted Types; no `innerHTML` from definitions |
| T9 | Sandbox escape via expressions | Restricted grammar; no `eval`; scoped access | Property-based and escape-attempt tests |
| T10 | Denial of service via expensive generated queries | Pre-execution cost guards; page fan-out budget | Per-tenant rate and cost limits; load shedding |
| T11 | Model provider data retention or training on client data | Contractual no-training and bounded retention; metadata-only egress | Region pinning; per-tenant opt-in for sample values |
| T12 | Operator or auditor accessing client data | Roles carry no data plane access | Audit of all administrative action |
| T13 | Entitlement revocation not taking effect | Short TTL on entitlement caches | Revocation event invalidation |
| T14 | Data egress via export | Exporter's entitlements applied; export audited | Per-tenant export policy |

## 12. Decisions Requiring Ratification

| # | Decision | Consequence if reversed later |
|---|---|---|
| S1 | Definitions are intent, never a boundary (P1) | Definition tampering becomes a data breach path |
| S2 | Data Gateway is the single enforcement point, verified by network policy and architectural test | Enforcement becomes unverifiable |
| S3 | Platform and data authorization are separate axes; Studio never widens access | Publication could grant data access — a fundamental breach of the EDM trust model |
| S4 | Entitlement scope in every cache key | Cross-user data leakage via cache |
| S5 | Entitlement-scoped catalog retrieval for authoring and AI alike | Attribute-name disclosure; systematically broken generated pages |
| S6 | Governance tiered by blast radius | Uniform friction, which users route around |
| S7 | Separation of duties for production publication (tenant-configurable) | Unreviewed changes reach regulated surfaces |
| S8 | Auditor and Platform Operator hold no data access | A permanently over-privileged operations team |
| S9 | Metadata-only AI egress by default; sample values opt-in and sensitivity-gated | Client data reaching a third-party model provider by default |
| S10 | Cross-tenant exemplars only from curated, scrubbed platform templates | Commercially sensitive structure leaks between clients |
| S11 | Immutable, append-only audit with a single correlation id end to end | Provenance and regulatory reconstruction become impossible |
| S12 | Adversarial entitlement tests gating CI | Enforcement regressions found by clients rather than by builds |
